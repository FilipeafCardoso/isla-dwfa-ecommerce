# Ficha 02 — perguntas de reflexão · reflection questions

**1. A regra "quantidade ≤ stock" está no `validate()` do serializer. Porque é que isso não substitui uma `CheckConstraint` (ou uma verificação em `select_for_update`) na base de dados?**

PT — O serializer só corre nos pedidos que passam pela API. O admin, um comando de `manage.py`, o `shell`, uma migração de dados ou outro serviço que escreva na mesma base de dados passam ao lado dele. Além disso a regra "quantidade ≤ stock" depende de outra linha (o produto) que pode mudar entre a validação e o `save()`: dois pedidos concorrentes validam ambos contra `stock = 3`, e ambos gravam — só uma verificação dentro de uma transação com `select_for_update` no produto (ou uma constraint, para regras de uma só linha como `quantity > 0`) garante a regra para todos os caminhos de escrita. O serializer dá a mensagem ao cliente; a base de dados dá a garantia.

EN — The serializer only runs for requests that go through the API; the admin, a management command, the shell, a data migration or another service writing to the same database bypass it. The rule also depends on another row (the product) that can change between validation and `save()`: two concurrent requests both validate against `stock = 3` and both write. Only a check inside a transaction with `select_for_update` on the product (or a constraint, for single-row rules such as `quantity > 0`) holds on every write path. The serializer gives the client a message; the database gives the guarantee.

**2. O endpoint de lista usa `PageNumberPagination`. Em que cenário trocariam para `CursorPagination`, que custo evita, e que condição o queryset tem de cumprir?**

PT — Quando a tabela cresce e os clientes pedem páginas longe do início (feeds, histórico de encomendas de anos): `OFFSET 100000` obriga o PostgreSQL a ler e deitar fora 100 000 linhas, e uma inserção entre duas páginas repete ou salta registos. A paginação por cursor usa `WHERE (created_at, id) < (…) ORDER BY … LIMIT 20`, que é um *seek* no índice — custo constante por página e resultados estáveis. Condição: o queryset tem de ter uma ordenação **total e estável** por um campo (ou tuplo) indexado e único — normalmente `-created_at` com desempate por `id`; sem ordenação determinística o cursor não tem significado, e perde-se o `count` e o salto para a página N.

EN — When the table is large and clients ask for pages far from the start: `OFFSET 100000` makes PostgreSQL read and discard 100 000 rows, and an insert between two pages repeats or skips records. Cursor pagination turns the page into an index seek (`WHERE (created_at, id) < (…) LIMIT 20`): constant cost per page and stable results. Condition: the queryset needs a total, stable ordering on an indexed, unique field or tuple (typically `-created_at` tie-broken by `id`); without a deterministic order the cursor is meaningless, and you give up `count` and jumping to page N.
